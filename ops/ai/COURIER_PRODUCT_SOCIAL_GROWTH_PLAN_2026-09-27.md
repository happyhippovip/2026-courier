# Courier Symphony — Product, Community & Growth Plan — 2026-09-27

## Founder intent
This document preserves the founder's stated product direction in operational language without silently changing the promise.

Courier Symphony is intended to remove copy/paste coordination between people and AI tools. The target experience is automation: a user states the goal, Courier coordinates the work, preserves state/evidence in the Ledger, continues safely, and asks the human only when a real human gate exists.

## €14 product ambition
Target offer: for about **€14**, a customer should be able to use Courier to go from an idea toward a complete project / website intended to earn money, rather than buying a chat window that still requires constant copy/paste.

This is a product and pricing target, not a guaranteed income claim. Courier must not promise that a generated site will actually earn a particular amount of money.

## Solo developers + LFG / LFM
Courier should support both:
- solo developers who want to build alone with automated AI coordination;
- people looking for collaborators;
- people/projects looking for contributors or makers.

Product language may use familiar community concepts such as **LFG / LFM**, while the UI must also explain them in plain language so non-gamers understand them.

The long-term flow should let a person publish what they are building, what help is needed, and what is already verified, then match or invite suitable people without turning the Ledger into a social feed.

## Package / pipeline idea
The founder's initial inspiration came from building a YouTube pipeline and finding the reusable pipeline concept simple enough to package.

Courier should support reusable, installable project/workflow packages where a useful invention can become a repeatable capability rather than being rebuilt manually by every customer.

A package must have provenance, versioning, permissions/capability boundaries, verification evidence, and a safe update path.

## Community invention exchange
Founder growth mechanism:
- people who contribute useful inventions/packages that Courier can safely incorporate can receive a target benefit of **3 months free**;
- their contribution can expand Courier for later users;
- early contributors/users should benefit from being early, while later users benefit from the growing verified package library.

The exact eligibility, moderation, licensing/IP terms, abuse controls, acceptance criteria, and economics MUST be defined before this is marketed as an unconditional entitlement.

No contribution becomes trusted merely because it was submitted. It enters through review, provenance, verification, compatibility, and safety gates.

## Daily downloadable updates
Target experience: frequent, potentially daily downloadable updates so customers can benefit from newly verified capabilities without rebuilding their installation.

Updates must be:
- versioned;
- signed/authenticated;
- rollback-capable;
- reproducible/auditable where practical;
- staged so a bad package/update cannot silently compromise every customer;
- tied to Ledger evidence and compatibility status.

"Daily" is a delivery ambition, not permission to ship unverified changes.

## Quantum-safe / future cryptographic migration
The product should be designed so update signing, identity, stored evidence, and long-lived security material can migrate toward post-quantum cryptography as standards/platform support mature.

Do not market Courier as "quantum secure" until the implemented cryptographic design, algorithms, key lifecycle, update chain, dependencies, and migration path have been independently verified.

Architectural requirement now: crypto agility — avoid hard-wiring the product to one irreversible signing/key scheme.

## How the Ledger connects everything
The Ledger is the trust/control spine, not just a task list. It should eventually connect:
GOAL → CONTRACT → TASK → CLAIM → EXECUTION → RESULT → VERIFY → RECONCILE → NEXT.

For packages/community updates it additionally needs provenance such as:
- package/version/source;
- contributor;
- declared capabilities/permissions;
- compatibility;
- verification state/evidence;
- signing/update identity;
- rollout/rollback state;
- cost/resource observations;
- whether work was reused instead of repeated.

This enables Courier to automate aggressively while remaining evidence-driven.

## Customer promise direction
Desired plain-language direction:
**Tell Courier what you want to build. Courier coordinates the work instead of making you copy and paste between AI windows. Build solo or find people to build with. Reuse verified packages and improvements from the community.**

Keep income claims separate: Courier can help create a monetizable project/site, but cannot guarantee revenue.

## Jobcenter / funding explanation
Plain-language project description:

Courier Symphony is planned as a software product for people who want to create digital projects without manually copying instructions and results between multiple AI tools. The system is intended to coordinate tasks automatically, record progress and verification in a Ledger, adapt resource use to the user's device, and continue work until a real decision or human action is required.

A planned entry offer is around €14 and is intended to make automated project creation accessible to solo developers and small creators. A customer may, for example, build a website or digital project intended for commercial use. The business model must not promise that the customer's project will actually generate income.

Courier is also intended to include a collaboration layer for solo developers and people looking for project partners (LFG/LFM), plus a verified package ecosystem. Useful user-contributed workflows or inventions may, under a future contribution program, qualify contributors for a target benefit such as three free months. Accepted contributions can then improve the reusable package library for other customers.

The update concept targets frequent downloadable improvements with provenance, verification, signing and rollback. The security architecture should remain crypto-agile so future post-quantum migration is possible without rebuilding the entire product.

## Order of execution
This vision MUST NOT derail the current core proof.

1. Finish canonical execution/verifier/reconciliation proof.
2. Prove no-copy/paste autonomous continuation on the core path.
3. Make Ledger/resource/cost truth customer-visible.
4. Productize reusable pipeline/packages.
5. Add safe package provenance/update/signing/rollback.
6. Add collaboration/LFG-LFM layer.
7. Define contribution/reward, licensing/IP and moderation rules.
8. Validate €14 unit economics with measured provider/resource costs.
9. Only then make quantified savings, revenue, security, or contribution-reward promises publicly.

The existing frozen final correction scope remains frozen until its proof gate is green.
