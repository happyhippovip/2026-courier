# COURIER COMPANY + LAUNCH OPERATING PLAN — 2026-09-27

Status: PUBLIC-SAFE COMPANY OPERATING PLAN
Principle: finish -> prove -> pilot -> learn -> productize -> scale

## Mission

Build Courier into a trustworthy work-continuation control plane that reduces human relay across tools, providers, sessions and restarts.

The company advantage is not "more models".
The advantage is durable execution truth, verified continuation, recovery and low human coordination overhead.

## Stage 1 — Core proof

Exit criteria:
- Trusted Ledger PASS + FROZEN
- Reliable Motor PASS
- Result -> Verify -> Reconcile -> NEXT_READY proven
- physical Zero-Human A->B with human relay count 0
- restart/no-replay proof
- bounded resources
- Proof Cards / Covered Surface / runtime binding

Do not scale marketing or feature scope before this is real.

## Stage 2 — Minimal pilot

First pilot can be manually onboarded.

Minimum visible product truth:
- Arbeitet
- Braucht dich
- Fertig
- Verified/Reported/Unknown distinction
- next action
- compact proof

Prepare:
- 3-5 real candidate users with context-loss / copy-paste / handoff pain
- one clear Goal per pilot
- human-confirmed Goal Contract
- baseline
- duration
- permission/data scope
- setup/support/provider-cost tracking
- deletion/retention process

For a paid external pilot, verify payment/privacy/tax/business prerequisites before launch.

## Stage 3 — Pilot decision

Measure:
- HIPG < 1.0 target
- RSR 100% on defined restart matrix
- NDR for first cohort
- setup minutes
- support burden
- provider cost
- payment willingness

Decision:
- 3-5/5 NDR: positive signal, prepare next gate
- 2/5: one bounded core/use-case iteration, then remeasure
- 0-1/5: review promise/use case/segment; do not respond with uncontrolled feature expansion

## Founder/operator workflow

The operator should not become the message bus.

Normal workflow:
- durable queue
- worker claim
- result
- harvester
- next READY
- automated continuation
- human only for real money/safety/permission/strategy gates

Long work sessions:
- checkpoint frequently
- clear stale context
- reuse permanent prompts
- prefer stable smaller wall to overloaded larger wall
- protect sleep by using durable overnight queues instead of manual "continue"

## Cost discipline

Optimize verified useful progress per human minute and per cost.

Never spend model/API budget on:
- repeated unchanged analysis
- duplicate reviewers
- idle polling
- re-reading already sufficient evidence
- keeping windows busy for appearance

Paid/API capacity is useful when it:
- closes a blocker
- changes a decision
- validates a required proof
- reduces real risk
- protects Courier correctness

## Shared capability flywheel + recurring updates

Canonical direction: `docs/COURIER_SHARED_CAPABILITY_UPDATE_FABRIC_2026-09-28.md`.

Courier's long-term business model includes a compounding shared-capability layer: proven, reusable work from one user may be sanitized, generalized, tested, versioned and offered to other users as optional capability packs. Private repositories, customer data, credentials and proprietary project content are not cross-customer distribution material by default.

Business loop:

REAL CUSTOMER WORK -> VERIFIED REUSABLE CAPABILITY -> SHARED LIBRARY -> LOWER SETUP/COST/DATA FOR OTHER USERS -> BETTER PRODUCT -> MORE REAL WORK.

Packaging should distinguish Core/Security Updates, cross-industry Shared Capability Packs, optional Domain Packs and Private Project Artifacts.

Target release rhythm after Core + positive pilot evidence:
- bounded continuous security/metadata checks;
- weekly stable update window when evidence justifies a release;
- monthly platform/capability rollup;
- emergency security fixes when necessary;
- no calendar-driven filler releases.

Updates should use signed manifests, content-addressed/deduplicated artifacts and delta/component delivery where safe. Users control optional capability installation and pinning. Product recovery should retain a durable Time-Machine-style history of versions, manifests, migrations, Last Known Good and rollback points.

Every release should preserve crypto agility and improve post-quantum migration readiness where standards/platform evidence supports it. Do not claim "quantum secure" without a concrete proven profile.
