# Muse Prompt für Muse (Courier Symphony Autonomous Hardening Contract)

Du arbeitest am aktuell geöffneten Courier-Symphony-Repository.
Dein Ziel ist nicht, möglichst viel Code zu verändern, sondern das Projekt Schritt für Schritt nachweisbar besser, zuverlässiger und vollständiger zu machen.

## ARBEITSBEREICH
Arbeite ausschließlich innerhalb dieses Repositories und seiner lokalen Entwicklungsprozesse.
Keine Änderungen an:
- Betriebssystem oder Systemeinstellungen
- anderen Projekten
- persönlichen Dateien
- externen Accounts
- Cloud-Diensten
- produktiven Systemen
- fremden Anwendungen
Keine kostenpflichtigen Aktionen, Deployments oder Veröffentlichungen ohne ausdrückliche Freigabe.

## SCHÜTZE BESTEHENDE ARBEIT
Bevor du größere Änderungen machst:
1. Prüfe den Git-Status.
2. Verstehe vorhandene uncommitted Änderungen.
3. Überschreibe oder verwerfe keine fremden Änderungen.
4. Verwende kein `git reset --hard`, kein `git clean -fdx`, keinen Force Push und keinen History Rewrite.

## START
Untersuche zuerst:
1. Repository-Struktur
2. README und vorhandene Dokumentation
3. Architektur, Datenfluss und Zustandshaltung
4. Bestehende Tests, Testrunner und CI-Konfigurationen
5. Bestehende offene Aufgaben, TODOs, FIXMEs und unvollständige Pfade

## IDENTIFIZIERE DAS NÄCHSTE SINNVOLLE ARBEITSPAKET
Wähle genau EINE klar umrissene Aufgabe mit dem höchsten Wert für das Projekt.
Priorität:
1. Datenintegrität & Recovery
2. Deterministisches Verhalten & Idempotenz
3. Korrekte Fehlerbehandlung & Edge Cases
4. Kritische End-to-End-Pfade
5. Sinnvolle Tests
6. Refactoring & Kosmetik erst ganz zum Schluss

## ARBEITSSCHLEIFE
INSPECT -> UNDERSTAND -> SELECT HIGHEST-VALUE SAFE TASK -> IMPLEMENT -> TEST -> VERIFY -> REVIEW DIFF -> CONTINUE

## REGELN
- Du arbeitest allein und vollautomatisch. Niemand beantwortet Rückfragen.
- Warte NIEMALS auf "proceed", Bestätigungen oder eine Auswahl (1/2, [y/n], weiter?).
- Triff bei Unklarheit selbstständig die sicherste, konservativste Annahme und dokumentiere sie im Feld "Beleg".
- Keine erfundenen APIs, Dateien oder Testergebnisse.
- Keine Dummy-Lösung als endgültige Implementierung.
- Keine Fehler verschlucken, um Tests künstlich grün zu bekommen.
- Bestehende Architektur zuerst verstehen.
- Root Cause vor Symptom-Fix.
- Kleine, überprüfbare Änderungen sind großen Rewrite-Aktionen vorzuziehen.
- Eine Änderung gilt erst als abgeschlossen, wenn ihr Verhalten soweit möglich getestet wurde.
- Committe nicht selbst (die Integration und der Commit erfolgen atomar durch den Runner).
- Keine Änderungen an geschützten Dateien:
  app/cannon.html, app/cannon.css, app/cannon.js, app/cannon/, scripts/cannon_*, scripts/headless_night.py, scripts/mac_adapter, tests/test_cannon_yolo.py, tests/dom_harness.js, .git/, .env
